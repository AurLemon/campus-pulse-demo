# 协作规范

## 工作方式

- 使用简体中文沟通，按当前对话中的称呼交流。先说明实质结果，再补充依据和限制，不套用固定赞同语或空泛免责声明。
- 开始前阅读项目规范、相关代码和 Git 状态，保留既有改动。按当前任务维护或重构，保留无关成果，不顺手升级无关依赖。本项目允许直接重构和开发数据库重建，不要求旧兼容层或迁移链。
- 除简单修改外，先整理目标、范围与执行步骤。目标清楚时直接推进，架构取舍、冲突和影响正确性的未知项用有序问题确认。
- 先核对现象与证据，再判断原因。明确区分观察、推断、计划与已验证结果，不把建议写成已确认需求。
- 小范围编辑直接验证，复杂流程先做最小闭环，再扩展。遇到反复失败的 API / 版本 / 环境问题，查官方文档和已知 Issue，不盲目重试。
- 直接指出具体问题，有误及时纠正，不使用客套话掩盖风险，也不把批评上升到人格。
- 项目文档直接描述规范和设计，不写个人提示词、聊天经过、要求来源、私人设备资料或“某人于某日要求”等叙述。

## 环境与工具

- 检查当前操作系统与已安装工具，不假定其他电脑拥有相同代理、密钥、技能或连接器。
- Node 项目统一使用 pnpm，开发编辑器以 VS Code 为准。依赖、Node 和包管理器版本以工程配置为准。
- 不擅自修改系统网络、代理和其他机器级配置。一次性采集、爬取数据或系统变更先明确方案与执行范围。
- 文档、PDF 和演示文稿任务使用适合的工具，渲染并核对排版，不能用源码检查替代视觉核验。

## 实现与验证

- 使用 TypeScript，数据契约优先 interface，避免不必要的 any。规则允许 any 不等于默认使用 any，类型困难先检查边界与结构。
- Service 聚焦本领域。普通查询和即时计算允许直接调用，跨业务后续动作需要事件时先列明节点、事件与 Payload Interface。
- 数据写入归所属领域，事务失败不发布成功事件。提交与后续副作用的先后关系必须明确。
- 内部来源、原始内容和费用记录必须保留，不冒充真实人员或真实用户效果统计。公共产品界面与 README 按业务呈现，来源说明留在独立工具文档。交付说明区分实际运行结果与内部内容生产。
- 不额外编写测试用例。运行现有检查和必要的实际行为核验，Build 通过不代表功能、交互、部署或跨平台已验收。
- 完成后运行 pnpm format，按范围执行 lint / 类型检查。代码变更执行 Build，纯 UI 小改动可免整体 Build。
- 清除临时 Debug 代码。任务结束不额外启动 Dev，需要交互验证而临时启动的进程用完关闭。
- 交付说明结果、关键变化、验证情况和未验证事项，信息足够即可，不重复总结。

## Git 与文档

- 未明确要求时不提交或推送。提交信息遵循 Conventional Commits，英文 type(scope)，冒号后使用中文说明。
- 行尾兼容 Linux / Windows，不提交环境密钥、数据库、缓存、node_modules 或构建产物。
- docs/ 内采用英文文件名，正文使用中文，保持链接同步。AGENTS.md 作为入口，细则放专题，不把私人提示词原文作为公共规范附录。
- 代码、配置与开发说明在 Project/，报告、截图、PPT、人员分工在上一级项目文档/，交付包在上一级交付文件/。
- 记录真实参与和成果，不伪造提交作者、贡献、时间或验收结论。
